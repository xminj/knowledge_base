# 第一阶段：内核训练——自定义二进制协议（第 1~7 天）
这一阶段的目标只有一个：**彻底搞懂 Netty 如何切出一帧完整数据**。后续的 VPN 透传、JT808 解析、FTP 控制通道，都建立在这个能力之上。

**第 1~2 天：定义协议与解码器骨架**

设计协议头：魔数（4 字节，固定值如 0xCAFEBABE）+ 版本（1 字节）+ 指令类型（1 字节）+ 数据长度（4 字节）+ JSON 消息体。关键参数直接对标成熟实现：`LengthFieldBasedFrameDecoder` 的构造参数设为 `maxFrameLength=10MB, lengthFieldOffset=6, lengthFieldLength=4, lengthAdjustment=0, initialBytesToStrip=0`。`initialBytesToStrip=0` 是有意为之——保留完整头部，让下游 Handler 能读到魔数和指令类型做校验。编码器继承 `MessageToByteEncoder`，先占位写入长度字段，写完消息体后回填实际长度。[](https://cloud.tencent.cn/developer/article/2654598?policyId=1004#2)

**第 3~4 天：粘包/半包单元测试**

用 `EmbeddedChannel` 写三个测试用例。用例一：一次性写入两条完整消息，断言解码器输出两个对象（粘包）。用例二：只写入一条消息的前半段，断言解码器输出为空；再写入后半段，断言输出一个对象（半包）。用例三：写入一条魔数错误的消息，断言解码器抛出异常或丢弃。这三个用例全绿，说明你真正理解了 `LengthFieldBasedFrameDecoder` 的行为，而不是“照着博客抄了一遍”。

**第 5~7 天：端到端最小服务**

客户端发心跳（指令类型=1），服务端回心跳响应（指令类型=2）。用 telnet 或 nc 手动发一条十六进制报文，观察服务端日志能否正确解析出指令类型和 JSON 内容。**验收标准**：能说清楚“为什么不用 `ByteToMessageDecoder` 手写切帧”——手写需要自己处理 `markReaderIndex/resetReaderIndex`，而 `LengthFieldBasedFrameDecoder` 已经帮你做了，且经过大量生产验证

# 第二阶段：二选一做深（第 8~28 天）
#### 选项 A：TCP 端口映射穿透（推荐，工程闭环最短）

参考 `net-tunnel-server` 或 `jquick-hub` 的透传思路。核心不是“写一个复杂的 VPN”，而是**用 Netty 的 Channel 完成两端的数据搬运**。

**第 8~10 天：打通“外部连接 → 服务端 → 客户端 → 内网目标”的链路**

服务端监听两个端口：`controlPort`（供内网客户端主动连入并保持长连接）和 `publicPort`（供外部用户访问）。当外部用户连上 `publicPort` 时，服务端通过已有的 control 通道发送一条“建立新连接”指令给客户端；客户端收到后，连接本地目标服务（如 127.0.0.1:8080），然后两端开始透传。关键代码：用 `Channel` 的 `writeAndFlush` 直接搬运 `ByteBuf`，**不做任何解析**。注意引用计数：从 `channelRead` 拿到的 `ByteBuf` 默认由 Netty 管理，如果要异步写入另一通道，需要 `retain()`。[](https://zhuanlan.zhihu.com/p/2072786876256236490?utm_medium=openapi_platform&utm_source=e10c3ad29e50)

**第 11~14 天：生命周期联动与背压**

任一端断开时，关闭关联的另一端。这是透传最容易出 bug 的地方：外部用户关闭浏览器，服务端必须通知客户端关闭到内网目标的连接，否则连接泄漏。另外加上 `setAutoRead(false)` 的背压控制：当对端写缓冲区满时，暂停本端读取，防止内存无限堆积。[](https://zhuanlan.zhihu.com/p/2072786876256236490?utm_medium=openapi_platform&utm_source=e10c3ad29e50)

**第 15~21 天：本地演示闭环**

本地起一个 Python HTTP 服务（`python -m http.server 8080`），穿透客户端将其映射到服务端的 9080 端口，用另一台机器或手机热点访问 `服务端IP:9080`，看到 Python 的目录列表。**验收标准**：访问成功，且访问结束后两端连接都正确关闭，服务端日志中没有 `LEAK` 告警。

**第 22~28 天（可选加餐）**：加一个简单的 token 鉴权——客户端连接 control 端口时先发一个固定长度的 token，服务端校验通过后才允许建立映射。不需要做复杂加密，重点是理解“在 Pipeline 的哪个位置插入鉴权 Handler”。

#### 选项 B：JT808 注册 + 位置上报解析

如果选这条路，不要从零开始造轮子，直接以 `yezhihao/jt808-server` 为参考，目标是**用自己的代码解析出与 `Elucidator` 工具一致的结果**。

**第 8~10 天：理解 JT808 报文结构并跑通参考项目**

先把参考项目跑起来，用 `Elucidator` 工具分析一条 0x0200 位置上报报文的十六进制数据，看清楚消息头（消息 ID、消息体属性、终端手机号、流水号）和消息体（报警标志、状态、纬度、经度、速度）各占几个字节、什么字节序。这一步的目的是建立“字节位置感”，不要急着写代码。

**第 11~18 天：用 Netty 实现 0x0100 注册消息解析**

JT808 的消息头中，“消息体属性”字段的低 10 位表示消息体长度。你可以用 `LengthFieldBasedFrameDecoder` 来切帧，但长度字段的位置和长度需要按 JT808 规范设置（长度字段在消息头的第 2~3 字节，共 2 字节）。解析出终端手机号后，回写 0x8100 注册应答，返回鉴权码（可以固定为 `"test_auth"`）。**验收标准**：用参考项目的模拟终端或 `Elucidator` 构造一条注册报文，你的服务端能解析出手机号并返回正确的应答报文。

**第 19~25 天：0x0200 位置上报解析**

解析纬度、经度（注意：JT808 中纬度单位是 1/10^6 度，经度同理）、速度（1/10 km/h）、方向。解析后存到内存 Map，并在控制台打印格式化结果。**验收标准**：用 `Elucidator` 工具对同一条报文的分析结果作为基准，你的解析输出与之一致。

**第 26~28 天**：把解析逻辑从 EventLoop 线程中剥离。在 `channelRead` 中只做解码和字段提取，落库或打印格式化结果丢到独立的 `ExecutorService`。这是 Netty 使用中最容易犯的错误之一：在 EventLoop 中做任何可能阻塞的操作，都会拖垮整条连接的心跳和后续数据。

# 第三阶段（可选）：FTP 双通道最小闭环（第 29~35 天）
FTP 的独特价值在于**控制连接与数据连接分离**，这是前面两个项目没有涉及的 Channel 管理模式。

**只做“登录 + 上传”**。控制通道（端口 21）用 Netty 的 `LineBasedFrameDecoder` 切分文本命令。解析到 `USER`/`PASS` 后返回 `230 Login successful`。解析到 `PASV` 时，动态开一个临时 `ServerBootstrap` 监听随机端口，返回 `227 Entering Passive Mode (h1,h2,h3,h4,p1,p2)`。客户端发 `STOR filename` 后，控制通道返回 `150`，数据通道接收 `ByteBuf` 写入本地文件，完成后控制通道返回 `226`。参考 `netty-ftp-receiver` 这个小项目作为起点即可。**验收标准**：用命令行 `ftp` 客户端或 FileZilla 能完成一次文件上传。
