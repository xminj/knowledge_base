
[[Ⅴ、从内存注册到Zookeeper]]阶段五使用zookeeper解决了服务发现。Consumer拿到了3个地址，随便选一个调，听起来没有问题。
但生产环境会存在以下问题：
* 3个节点，怎么选？随机可能存在短期全部打到一个节点上。
* 一个节点挂了，怎么办？调用失败，用户看到报错。
* 一个节点不响应，怎么办？等5秒超时，然后超时。
* 一个节点连续失败10次，还要调吗？每次白等5秒。
* 刚失败的节点，还要再试吗？大概率也是失败。
能调通和抗的住之间，隔着5个问题

# 一、先想清楚：这五个机制各自解决什么？

| 问题        | 机制   | 触发时机   | 作用范围 |
| --------- | ---- | ------ | ---- |
| 这次调那个？    | 负载均衡 | 每次调用前  | 单次选择 |
| 一个挂了怎么办？  | 失败重试 | 单次失败   | 单词调用 |
| 一直不响应？    | 超时控制 | 超时     | 单词请求 |
| 连续失败？     | 熔断   | 联系N次失败 | 节点级  |
| 刚失败过还调用吗？ | 黑名单  | 单次失败   | 节点级  |
三者关系图
```text
调用请求
   │
   ▼
[黑名单] → 过滤掉最近失败的节点
   │
   ▼
[熔断器] → 过滤掉熔断中的节点
   │
   ▼
[负载均衡] → 从可用节点里选一个
   │
   ▼
[超时控制] → 发请求，等 N 秒
   │
   ├─ 成功 → 返回
   │
   └─ 失败 → [重试] → 换下一个节点
              │
              ▼
         [黑名单] 记录失败节点
```
这五个机制不是堆砌，而是层层过滤+逐级兜底

# 二、设计决策1：三种负载均衡，怎么选

候选方案

| 策略    | 优点      | 缺点      | 使用场景   |
| ----- | ------- | ------- | ------ |
| 随机    | 简单、无状态  | 短期可能不均  | 节点性能相近 |
| 轮询    | 分布均匀    | 不考虑性能差异 | 通用     |
| 一致性哈希 | 节点变化影响小 | 实现复杂    | 需要会话粘性 |
**都实现，配置切换**
* 满足不同场景需求不同
* 学习价值在于理解每种策略的代价
* 配置化设计更接近生产框架
轮询的实现有一个坑：
```java 
// 有 bug 的写法
int i = index.getAndIncrement() % addresses.size();

// 正确的写法
int i = Math.abs(index.getAndIncrement() & Integer.MAX_VALUE) % addresses.size();
```

为什么：AtomicInteger长期递增会溢出为负数，`-1 % 3 = -1` ，索引越界

# 三、设计决策2：一致性哈希，到底解决什么问题

**普通哈希不够用吗？**
```text
节点：[A, B, C]
key 分布：hash(key) % 3
```
问题：C挂了，节点编程[A , B]，`hash(key) % 2`的结果和 `% 3`完全不同
**结果：几乎所有的key都要重新映射**

**一致性哈希**
* 把节点和key都映射到一个0~2^32的 环上
* 每个key顺时针找第一个节点
* 节点变了，只影响相邻的一段key
实现要点：
```java
// 1. 环形结构用 TreeMap
TreeMap<Long, String> ring = new TreeMap<>();

// 2. 每个真实节点映射 160 个虚拟节点
for (String address : addresses) {
    for (int i = 0; i < 160; i++) {
        ring.put(hash(address + "#" + i), address);
    }
}

// 3. 顺时针找节点
SortedMap<Long, String> tail = ring.tailMap(hash(key));
Long nodeHash = tail.isEmpty() ? ring.firstKey() : tail.firstKey();
return ring.get(nodeHash);
```

为什么需要虚拟节点
* 3个真实节点，分布可能不均匀
* 每个真实节点映射160个虚拟节点，分布更均匀
* 节点数越多，虚拟节点效果越明显

# 四、设计决策3：为什么黑名单要过期时间？

**黑名单的初衷**：节点失败了，短期内别再选它
如果永久拉黑;
* 节点只是网络闪断
* 30秒后恢复，但已经被永久拉黑
* 永远恢复不了

方案对比

| 方案        | 问题        |
| --------- | --------- |
| 永久拉黑      | 节点恢复后无法回归 |
| 定时清理      | 需要额外线程    |
| 带过期时间的黑名单 | 简单、自动恢复   |
实现：
```java 
private static final long BLACKLIST_DURATION = 30_000;
public void add(String address) {
    blacklist.put(address, System.currentTimeMillis() + BLACKLIST_DURATION);
}
public boolean isBlacklisted(String address) {
    Long expireAt = blacklist.get(address);
    if (expireAt == null) return false;
    if (System.currentTimeMillis() > expireAt) {
        blacklist.remove(address);  // 过期自动移除
        return false;
    }
    return true;
}
```

**"懒删除"的设计**
* 不启动后台线程
* 在判断时顺便请求过期的
* 用读操作触发清理，零额外开销
