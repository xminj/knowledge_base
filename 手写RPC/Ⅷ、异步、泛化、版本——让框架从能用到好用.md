[[Ⅶ、为什么 Dubbo 能用一个 @Reference 搞定一切]]已经让框架用起来想Dobbo，但是还不够
* 同步调用太慢：3个调用串行9秒，能不能并发？
* 没有接口Jar怎么调用：网关，测试平台不可能引入所有的接口。
* 多版本怎么共存：v1和v2同时在线，怎么区分？
本节内容解决异步调用+泛化调用+版本管理这三个问题。

# 一、异步调用：从串行9秒到并发3秒
同步的瓶颈：
```java
String a = serviceA.call();  // 3 秒
String b = serviceB.call();  // 3 秒
String c = serviceC.call();  // 3 秒
// 总耗时 9 秒
```

异步的解法：
```java
CompletableFuture<String> fa = serviceA.callAsync();
CompletableFuture<String> fb = serviceB.callAsync();
CompletableFuture<String> fc = serviceC.callAsync();
CompletableFuture.allOf(fa, fb, fc).join();
```
 接口定义
 ```java
 public interface HelloServiceAsync {
    CompletableFuture<String> sayHelloAsync(String name);
    CompletableFuture<Integer> addAsync(int a, int b);
}
 ```

为什么单独定义一个Async接口，不直接把sayHello改成返回`CompletableFuture`
* 破坏兼容性，老客户端会挂
* 同步和异步各有使用场景，应该共存

# 二、反直觉的坑：服务端为什么不直接返回CompletableFuture?
最初的实现：
客户端代理层判断返回值是CompletableFuture，走异步路径。服务端`RpcServerHandler`
```java
Object result = method.invoke(service, request.getArgs());
response = RpcResponse.success(request.getRequestId(), result);  // ← 直接把 CompletableFuture 塞进去
```
现象：所有的调用都超时
```text
TimeoutException
    at CompletableFuture.timedGet(...)
```
`CompletableFuture`不可序列化，也不能跨进程"传递"，它依赖创建它的JVM里的线程池
* 服务端创建的`CompletableFuture`只能存在服务端的JVM
* 序列化发到客户端后，客户端反序列化出来的不是同一个Future，也不会自动完成
* 客户端future.get()等的是一个永远不会完成的壳，必然会超时
修复：服务端`method.invoke`之后，如果返回的值是`CompletableFuture`，先等join()完成，在把真实结果发回去。
```java
Object result = method.invoke(service, request.getArgs());
result = resolveResult(result);   // CompletableFuture 先 join

private Object resolveResult(Object result) {
    if (result instanceof CompletableFuture) {
        return ((CompletableFuture<?>) result).join();
    }
    return result;
}
```
