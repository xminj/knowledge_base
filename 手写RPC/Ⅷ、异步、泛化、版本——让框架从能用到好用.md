[[Ⅶ、为什么 Dubbo 能用一个 @Reference 搞定一切]]已经让框架用起来想Dobbo，但是还不够
* 同步调用太慢：3个调用串行9秒，能不能并发？
* 没有接口Jar怎么调用：网关，测试平台不可能引入所有的接口。
* 多版本怎么共存：v1和v2同时在线，怎么区分？
本节内容解决异步调用+泛化调用+版本管理这三个问题。

# 一、异步调用：从串行9秒到并发3秒
同步的瓶颈：
```java
String a = serviceA.call();  // 3 秒
String b = serviceB.call();  // 3 秒
String c = serviceC.call();  // 3 秒
// 总耗时 9 秒
```

异步的解法：
```java
CompletableFuture<String> fa = serviceA.callAsync();
CompletableFuture<String> fb = serviceB.callAsync();
CompletableFuture<String> fc = serviceC.callAsync();
CompletableFuture.allOf(fa, fb, fc).join();
```
 接口定义
 ```java
 public interface HelloServiceAsync {
    CompletableFuture<String> sayHelloAsync(String name);
    CompletableFuture<Integer> addAsync(int a, int b);
}
 ```

为什么单独定义一个Async接口，不直接把sayHello改成返回`CompletableFuture`
* 破坏兼容性，老客户端会挂
* 同步和异步各有使用场景，应该共存

# 二、反直觉的坑：服务端为什么不直接返回CompletableFuture?
最初的实现：
客户端代理层判断返回值是CompletableFuture，走异步路径。服务端`RpcServerHandler`
```java
Object result = method.invoke(service, request.getArgs());
response = RpcResponse.success(request.getRequestId(), result);  // ← 直接把 CompletableFuture 塞进去
```
现象：所有的调用都超时
```text
TimeoutException
    at CompletableFuture.timedGet(...)
```
`CompletableFuture`不可序列化，也不能跨进程"传递"，它依赖创建它的JVM里的线程池
* 服务端创建的`CompletableFuture`只能存在服务端的JVM
* 序列化发到客户端后，客户端反序列化出来的不是同一个Future，也不会自动完成
* 客户端future.get()等的是一个永远不会完成的壳，必然会超时
修复：服务端`method.invoke`之后，如果返回的值是`CompletableFuture`，先等join()完成，在把真实结果发回去。
```java
Object result = method.invoke(service, request.getArgs());
result = resolveResult(result);   // CompletableFuture 先 join

private Object resolveResult(Object result) {
    if (result instanceof CompletableFuture) {
        return ((CompletableFuture<?>) result).join();
    }
    return result;
}
```

# 三、泛化接口：不依赖接口Jar的RPC
场景：网关要路由到任意服务，不可能引入所有接口Jar
解法：
```java
genericService.$invoke(
    "com.xxx.HelloService",
    "sayHello",
    new String[]{"java.lang.String"},
    new Object[]{"rpc"}
);
```
原理：用字符串代替方法签名，服务端靠反射执行
实现要点：
* 客户端代理把 `interfaceName`、`methodName`、`paramTypes`、`args` 打包成 `$invoke` 请求
* 服务端识别`$invoke`，解析参数，用户反射调用
* 返回结果

# 四、一个接口两个实现，泛化调用该选谁

场景
```java
@RpcService(version = "1.0")
public class SpringHelloServiceAsyncImpl implements HelloServiceAsync, HelloService { ... }
@RpcService
public class SpringHelloServiceImpl implements HelloService { ... }
```
一个 `HelloService`，两个实现：一个带版本 `1.0`，一个无版本。
现象：泛化调用永远只调用到 `SpringHelloServiceImpl`（无版本那个），调不到`SpringHelloServiceAsyncImpl`（1.0 那个）。
原因：服务注册时，`serviceMap` 有两个 key：

| 服务                          | 写入Key                                                  |
| --------------------------- | ------------------------------------------------------ |
| SpringHelloServiceImpl      | HelloService:                                          |
| SpringHelloServiceAsyncImpl | `HelloService:1.0` 和 `HelloService:`（`putIfAbsent` 兜底） |
`putIfAbsent`的意思*如果不存在才放*，如果 `SpringHelloServiceImpl` 先注册，`HelloService:` 已经是它了，`SpringHelloServiceAsyncImpl` 的兜底注册被丢弃。
而泛化调用查的是：
```java
Object service = serviceMap.get(interfaceName + ":");  // 永远拿到 SpringHelloServiceImpl
```
**修复**：泛化调用必须支持带版本。
**改造后的 `$invoke`**：
```java
public interface GenericService {
    Object $invoke(String interfaceName, String methodName,
                   String[] paramTypes, Object[] args);
    // 带版本的重载
    Object $invoke(String interfaceName, String version, String methodName,
                   String[] paramTypes, Object[] args);
}
```
**服务端泛化分支**：
```java
// args = {interfaceName, version, methodName, paramTypes, args}
String interfaceName = (String) args[0];
String version       = (String) args[1];
String methodName    = (String) args[2];
// ...
String key = interfaceName + ":" + version;
Object service = serviceMap.get(key);
```
**同时，`registerService` 也要改**：不要给"有版本的服务"写无版本兜底 key。
```java
public void registerService(String interfaceName, String version, Object service) {
    String v = (version == null) ? "" : version;
    serviceMap.put(interfaceName + ":" + v, service);
    // 只有无版本服务，才写无版本兜底 key
    if (v.isEmpty()) {
        serviceMap.putIfAbsent(interfaceName + ":", service);
    }
}
```
改后

| Key              | 值                           | 语义  |
| ---------------- | --------------------------- | --- |
| HelloService:1.0 | SpringHelloServiceAsyncImpl | 带版本 |
| HelloService:    | SpringHelloServiceImpl      | 无版本 |
**调用方按需选**：
```java
// 调 1.0
genericService.$invoke("HelloService", "1.0", "sayHello", ...);
// 调无版本
genericService.$invoke("HelloService", "sayHello", ...);
```

# 五、版本管理：v1和v2怎么共存
**问题**：`HelloService` 有 v1 和 v2，`interfaceName` 相同，怎么区分？
解法：
```java
@RpcService(version = "1.0")
public class HelloServiceImplV1 implements HelloService { ... }

@RpcService(version = "2.0")
public class HelloServiceImplV2 implements HelloService { ... }

@RpcReference(version = "1.0")
private HelloService helloServiceV1;

@RpcReference(version = "2.0")
private HelloService helloServiceV2;
```
ZK路径
```text
/rpc/com.xxx.HelloService/1.0/10.0.0.1:8080
/rpc/com.xxx.HelloService/2.0/10.0.0.2:8080
```
**服务发现 key**：`interfaceName:version` → ZK 路径 `interfaceName/version`。

# 六、参数校验：客户端+服务端校验
客户端校验：快速失败，节省网络往返
```java
public static void validate(RpcRequest request) {
    Object[] args = request.getArgs();
    if (args == null) return;
    for (int i = 0; i < args.length; i++) {
        if (args[i] == null) {
            throw new RpcException(String.format(
                    "参数校验失败: %s.%s 的第 %d 个参数为 null",
                    request.getInterfaceName(), request.getMethodName(), i + 1));
        }
    }
}
```
**服务端校验**：防御性编程，防止绕过。
```java
if (request.getArgs() != null) {
    for (Object arg : request.getArgs()) {
        if (arg == null) {
            throw new RpcException("参数不能为 null");
        }
    }
}
```
