
[[Ⅰ、从Socket+动态代理开始]]使用150行代码跑通RPC的核心流程。但准备加Netty时，发现一个问题：**改一处，动全身**
* 想换序列化方式？需要同时改客户端和服务端两处
* 想换注册中心? 需要改代理类
* 想加负载均衡？需要改`SimleClient`

代码能跑，但每加一个功能都需要修改核心逻辑，这不是RPC核心框架该有的样子。
于是：不新增任何新功能，把模块拆分

# 一、先想清楚：什么会变，什么不会变

拆模块的本质，是回答一个问题：**这个框架里，哪些东西是可替换的？**
把RPC的组件列出来，逐个考虑会不会变

| 组件               | 是否会变                          | 结论      |
| ---------------- | ----------------------------- | ------- |
| 协议对象(RpcRequest) | 稳定                            | 放common |
| 序列化方式            | 会变（JDK/Hessian/JSON/Protobug） | 抽象成接口   |
| 注册中心             | 会变（内存/ZK/Nacos）               | 抽象成接口   |
| 通信方式             | 会变（socket/Netty/Mina）         | 独立模块    |
| 负载均衡             | 会变（随机/轮询/一致性哈希）               | 抽象成接口   |
| 代理方式             | 会变（JDK/CGLB/Javassist）        | 独立模块    |
**核心洞察：变的部分抽象成接口，不变的部分沉淀到common**
这就是依赖倒置-**上层依赖接口，下层提供实现**

# 二、拆成什么样

最终项目结构
```text
mini-rpc/
├── rpc-common/          # 接口、协议对象、异常、常量（谁都不依赖）
├── rpc-serialization/   # 序列化实现（依赖 common）
├── rpc-registry/        # 注册中心（依赖 common）
├── rpc-remoting/        # 通信层（依赖 common + serialization）
├── rpc-core/            # 代理、负载均衡（依赖 common + remoting）
└── rpc-demo/            # 示例（依赖所有）
```
**依赖方向永远都是单向的**：`demo->core->remoting->serialization->common`

**为什么这样拆**

| 模块            | 职责               | 为什么独立           |
| ------------- | ---------------- | --------------- |
| common        | 只定义"什么"，不定义"怎么做" | 被所有模块依赖，必须零外部依赖 |
| serialization | 只做序列化            | 换序列化方式不影响其他     |
| registry      | 只做注册发现           | 换注册中心不影响其他      |
| remoting      | 只做网络通信           | 换Netty不影响其他     |
| core          | 代理、负载均衡、编排       | 业务和兴、变化最频繁      |

# 三、设计决策1：为什么"先拆模块"而不是"先加Netty"

存在两条路：
A：先加功能，最后重构
B：先拆模块，在慢慢加功能

选择B的理由：
* 接口定义的过程=理解RPC扩展点的过程。
* 每个功能只改一个模块
代价：
* 这个阶段结束什么功能都没有增加，容易有"没进展"的错觉
* 需要写更多的样板代码（接口+空实现）
* 一个人做项目，容易怀疑是不是设计过度

# 四、设计决策2：为什么协议里要加requestId？

阶段Ⅰ：同步Socket，一个请求一个链接，发完就等，拿到就是它的响应
阶段Ⅱ：Netty异步通信，多个请求共用一条链接，响应回来时，怎么知道是那个请求的？

这就是为什么需要增加requestId的原因

# 五、设计决策3：为什么用"长度前缀"而不是分隔符？

网络传输消息时，怎么区分一条消息的边界？

候选方案：

| 方案   | 原理         | 优点       | 缺点          |
| ---- | ---------- | -------- | ----------- |
| 分隔符  | 读到`\n` 算一条 | 实现简单     | 内容里出现分隔符就误判 |
| 固定长短 | 每条消息定长     | 解析快      | 不灵活，浪费      |
| 长度前缀 | 先读长度，在读内容  | 二进制安全，通用 | 需要约定长度字段大小  |
选择长度前缀理由
* 二进制安全，内容里即使出现了`\n` 也不影响解析
* 阶段Ⅱ中Netty协议里，长度字段依然存在，只是前面多了魔数、版本、序列化类型等。
	* 阶段Ⅱ协议
		```text
		+--------+--------+--------+--------+--------+--------+
		| 魔数   | 版本   | 序列化 | 类型   | 请求ID | 长度   | body |
		+--------+--------+--------+--------+--------+--------+
		```

# 六、问题记录

 *  模块循环依赖
	 * 现象：`rpc-core`依赖`rpc-remoting`、`rpc-remoting`又向依赖`rpc-core`，就存循环依赖
	 * 原因：把代理（core）和通信（remoting）的职责混淆
	 * 解决：明确依赖方向，core依赖remoting，反之不能依赖。remoting只负责怎么发送字节，不关心发给谁
 * Demo模块的API放哪里
	 * 现象：Provide和Consumer都要用HelloService接口，放那合适？
	 * 原因：接口是契约，不属于Provide也不属于Consumer
	 * 解决：单独将rpc-demo-api模块，Provide和Consumer都依赖它。这也是Dubbo的做法-服务接口独立成模块
 * 内存注册中心跨进程不可见
	 * 现象：Provide注册了，Consumer却拿不到
	 * 原因：`SimpleServiceRegistry` 是个内存Map，两个进程各有各的。
	 * 解决：阶段Ⅰ的Demo临时在Consumer里手动注册同一地址，验证接口抽象。
